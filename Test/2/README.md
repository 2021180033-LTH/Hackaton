# Forensic_G v3 — 오류 정정과 원본 기준 보정을 통한 시청 사본 식별

시청자가 재생을 요청할 때 그 접속에 고유한 영상 사본을 생성합니다. 유출 의심 영상에서 VideoSeal 코드를 복원하면 **업로더가 아니라 그 사본을 요청했던 시청 세션**을 조회합니다.

## 실행과 시연

1. `Forensic_G.exe` 또는 `outputs/Forensic_G_실행.cmd`를 실행합니다. 로컬 제작자 관리 화면이 열립니다.
2. 관리 화면에서 `sample.mp4`나 30초/100 MB 이내 원본 영상을 등록합니다. 이 단계에서는 시청자용 코드를 발급하지 않습니다.
3. **시청 링크·세션**에서 `/watch/{영상ID}` 링크를 확인합니다. 제작자는 이 링크만 전달합니다. 관리자 주소는 전달하지 마세요.
4. 시청자가 시청 페이지에서 **재생 준비 후 시청**을 누르면, 서버가 그 요청의 IP·브라우저 쿠키 ID·새 재생 세션을 기록하고 고유 코드를 삽입합니다.
5. 저장 MP4에서 코드 인증이 통과한 뒤, 해당 시청 브라우저에만 사본을 제공합니다. 같은 영상이어도 시청 요청마다 코드가 다릅니다.
6. 시청 페이지에서 **현재 시청 사본 저장**으로 파일을 저장합니다. 제작자 관리 화면의 **유출본 검사**에 이 파일이나 반전/변형한 파일을 넣습니다.
7. 검사 화면에서 위치 보정 기준 원본을 선택합니다. 기본값은 등록 원본 최대 8개를 자동 비교하며 동일한 파일은 중복 비교하지 않습니다.
8. 결과에서 **사본 식별번호**, 오류 정정 비트 수, 방향·화면 위치 보정 여부와 해당 시청 세션을 확인합니다.

**v3 오류 정정은 새로 재생을 요청하여 발급한 사본에 적용됩니다.** 이미 저장한 이전 형식의 영상에 오류 정정 신호가 소급 추가되지는 않습니다. 이전 사본도 기존 검출 방식으로 검사합니다.

시청자 A/B를 구별하는 데모는 다른 브라우저 프로필 또는 시크릿 창의 독립 쿠키 환경에서 같은 시청 링크를 열면 됩니다. **새 재생 세션** 버튼으로 동일 브라우저에서도 새 사본을 요청할 수 있지만 브라우저 ID 자체는 그대로입니다.

현재 서버는 **127.0.0.1에만 바인딩**합니다. 이 PC의 모든 테스트 접속 IP는 127.0.0.1이며, 실제 외부 IP를 꾸며 넣지 않습니다. 다른 노트북의 IP를 기록하는 LAN/인터넷 서비스는 별도의 배포·인증·프록시 구성이 필요합니다. 임의로 보내는 `X-Forwarded-For`나 요청 본문의 IP/이름은 식별 근거로 사용하지 않습니다.

제작자 화면은 EXE가 여는 관리 주소로 접근합니다. 관리 접근 정보는 현재 Windows 계정의 DPAPI 보호 키에서 파생되며 `data/admin_url.txt`는 로컬 실행을 위한 접근 링크입니다. `data/` 폴더는 공유하거나 GitHub에 올리지 마세요. 브라우저 탭을 닫아도 서버는 실행됩니다. 직접 실행한 EXE 콘솔을 닫거나, 숨겨 실행한 경우 이 폴더의 Forensic_G.exe만 종료하세요.

## fingerprint가 뜻하는 것

- **콘텐츠 fingerprint / perceptual hash:** 영상 특징을 계산하여 원본 또는 유사 영상을 찾습니다. 영상 내용이 같으면 여러 시청자의 사본을 구별하는 수단이 되지 못합니다.
- **시청자별 forensic fingerprint:** 사본마다 다른 코드를 삽입하여 어느 재생 세션에 제공됐는지 구분합니다. 현재 프로그램이 구현한 것은 **VideoSeal 기반 시청 세션별 워터마킹**입니다.
- 현재 프로그램은 PDQ/vPDQ 같은 별도의 콘텐츠 fingerprint 검색 엔진을 구현하지 않았습니다. 브라우저 하드웨어 fingerprint를 수집하지도 않습니다. 브라우저 ID는 임의의 쿠키 번호입니다.

## 저장하는 정보와 그 의미

영상 안에는 256비트 코드만 넣습니다. IP, 이름, 브라우저 정보는 영상 안에 그대로 쓰지 않고 로컬 장부에 연결합니다.

```
bits   0..2   : 형식 식별 비트 101
bits   3..66  : 사본 ID, 64 random bits (장부에서 중복 검사)
bits  67..130 : HMAC-SHA256(secret, "Forensic_G/ecc-v3/" + 사본 ID 8 bytes)의 첫 64 bits
bits 131..254 : BCH(255,131), t=18 오류 정정 비트 124개
bit       255 : 0 padding (검출 시 사용하지 않음)
```

영상 ID·IP·브라우저 정보는 사본 ID로 장부에서 조회합니다. 무작위 데이터를 일반 압축한 것이 아니라, 영상에 담을 필드를 줄이고 124비트를 오류 정정에 할당한 구조입니다. 모델 입력 길이는 여전히 256비트이므로 삽입 연산이 그만큼 줄어드는 것은 아닙니다.

새 형식은 64비트 인증 태그를 사용합니다. 이전 형식의 96비트 태그보다 짧다는 설계상 절충이 있습니다. 태그를 통과하고 실제 발급 완료 기록과도 정확히 일치해야 시청 세션을 표시합니다. 이전 형식은 FG 헤더 + 영상 ID 64비트 + 사본 ID 64비트 + HMAC 96비트를 그대로 지원합니다.

시청 사본 레코드의 `issuance_context`는 `viewer_playback`입니다.

- `viewer_request_ip`: `/api/playback/start`에 접속한 소켓의 주소. 업로드 요청 주소가 아닙니다.
- `viewer_browser_id`: 시청 페이지에서 발급한 HttpOnly/SameSite 쿠키. 물리적 기기의 고정 ID가 아닙니다.
- `playback_session_id`: 재생 요청마다 새로 발급하는 임의 번호.
- `first_media_request_ip`, `first_media_request_at`: 실제 MP4 요청이 들어왔을 때 기록합니다. 준비가 끝났다는 이유로 미디어 전송을 기록하지 않습니다.
- `playback_events`: 브라우저의 `playing`/`ended` 이벤트를 별도로 기록합니다. `evidence_type=client_reported`이며 사람이 실제로 봤다는 확정 증거가 아닙니다.
- `user_agent`: 재생 요청 브라우저가 보낸 환경 설명. 위조 가능하므로 신원 인증 정보가 아닙니다.

로그인 신원/실명 인증은 포함하지 않았습니다. IP 공유, VPN, 쿠키 복사, 사본 재전달로 인해 이 정보만으로 실제 유출자를 확정할 수 없습니다. 이미 발급된 코드를 다른 영상에 재삽입하는 등의 공격도 막지 못합니다.

기존 버전의 수동 발급 기록은 삭제하지 않았습니다. UI에 **이전 데모 · 시청자 정보 아님**으로 구분하며, 예전 발급 요청자를 시청자로 바꿔 해석하지 않습니다. 예전 `/api/issue`는 410으로 거절합니다.

## 반전과 변형 처리

검사 시 최대 32프레임을 추출해 256×256으로 정규화합니다. 각 프레임을 정방향·좌우 반전·상하 반전·양쪽 반전의 4가지 방향으로 각각 검사합니다. 방향별 로짓 평균으로 코드를 복원하고 BCH 오류 정정 후 HMAC를 확인합니다. 새 형식은 255개 코드 비트 중 임의의 최대 18개 오류를 교정합니다. 실패한 경우 신뢰도가 낮은 8비트 중 최대 3비트를 뒤집는 제한된 재시도도 수행하지만, 18비트를 초과하는 오류의 복구를 보장하지 않습니다. 이전 형식에는 최대 2비트 보정을 적용합니다.

기본 검사가 실패하면 원본 프레임으로 방향, 가로·세로 배율, 이동량을 추정합니다. C++ LibTorch에서 저해상도 장면 차이를 최소화하는 위치 보정을 수행합니다. 추정 오차가 큰 기준 영상은 제외합니다. **보정 영상에는 의심 영상의 픽셀만 사용하며, 없어진 영역은 0으로 채웁니다. 원본이나 발급된 다른 시청자의 워터마크를 합성하지 않습니다.** 원본과 유사하다는 점은 식별 근거가 아닙니다.

이 보정은 화면 전체에 일정한 축방향 확대·축소·신축·이동·반전을 가정합니다. 시간 편집, 회전·원근 왜곡, 장면별로 달라지는 줌은 추정하지 않습니다. 등록 원본 8개 제한을 넘으면 검사 화면에서 해당 원본을 직접 선택하세요.

발급 장부의 정답이나 예상 시청자 ID를 검출기에 전달하지 않습니다. 서로 다른 유효 코드가 여러 방향에서 발견되면 모호하다고 판단하여 연결하지 않습니다. 여러 방향에서 같은 유효 코드가 나오면 한 코드로 합칩니다.

보고서의 `channel_recovery.orientation`은 **검출에 사용한 입력 변환**입니다. 모델이 여러 방향에서 같은 코드를 읽을 수 있으므로, 실제 편집자가 수행한 반전 종류를 판정한 값은 아닙니다.

같은 8초·720p 합성 게임 영상에 시청자 A/B용 서로 다른 코드 2개, 강도 0.4를 적용했습니다. 변형 후 H.264 CRF23, medium, yuv420p로 재압축했습니다.

- 좌우 반전: 2/2.
- 상하 반전: 2/2.
- 좌우·상하 반전: 2/2.
- 좌우 반전 + 640×360 축소: 2/2.
- 상하 반전 + 가로 1.5배 신축(1920×720): 2/2.

- 좌우 반전 + 약 1.5배 중앙 확대 크롭: **0/2, 식별 실패**.

- 4방향 검사 엔진 시간: 이 장비에서 약 2.47~3.97초. RTX 3060 Laptop 6 GB. HTTP 업로드 시간 제외.

상세 결과: `../outputs/Forensic_G_시청자_반전_검증.json` 및 `tests/results/viewer_*/report.json`.

이는 한 영상/두 코드에 대한 결과이며 일반 성공률이나 임의의 변형에 대한 보장이 아닙니다. 이전 검사에서도 320×180 축소와 약 1.5배/2배 중앙 확대 크롭에 실패했습니다. 임의 회전, 원근·비선형 왜곡, 움직이는 줌, 화면 촬영, 고의적 워터마크 제거, 여러 사본 결합은 검증하지 않았습니다.

v3에는 원본 기반 위치 보정과 BCH 오류 정정을 추가했습니다. 기존 실패 영상을 모두 복구한다는 뜻은 아닙니다. 더 강한 크롭 대응에는 영역별 반복 삽입 등의 추가 설계가 필요할 수 있습니다. 콘텐츠 fingerprint가 잘 맞더라도 그것만으로 시청자의 워터마크 코드가 복원됐다고 주장하면 안 됩니다.

## 현재 API

모든 POST는 `X-Forensic-G: 1`이 필요합니다. 브라우저는 동일 출처만 허용합니다. 제작자와 시청자 쿠키를 구분합니다.

제작자 전용:

```
GET  /api/state
POST /api/assets          영상 바이너리; Content-Type: application/octet-stream
                         X-Filename: encodeURIComponent(filename)
POST /api/inspect         의심 영상 바이너리
                         X-Reference-Asset: auto | none | 등록 원본 ID (기본 auto)
GET  /original/{asset_id} 제작자만 원본 조회 가능
GET  /report/{report_id}  검사 JSON
```

시청자 전용:

```
GET  /watch/{asset_id}             시청 페이지, fg_viewer 쿠키 생성
GET  /api/watch/{asset_id}         영상 제목·길이만 조회
POST /api/playback/start           {"asset_id":"..."}
                                  IP/이름/예상 코드 입력을 받지 않음
GET  /api/playback/{id}            본인 시청 사본 준비 상태
GET  /stream/{id}                  본인 쿠키로만 검증된 MP4 제공
GET  /stream/{id}?download=1       동일 사본 다운로드
POST /api/playback/{id}/events     {"event":"playing","position_seconds":0.5}
                                  또는 ended; client_reported로 기록
```

작업은 한 번에 하나만 처리합니다. 다른 작업 중이면 시작 요청에 409를 반환합니다. `ready` 전에는 영상을 전달하지 않고 검증 실패 시 `verification_failed`를 표시합니다. 공개 시청 페이지에는 원본 주소/관리 장부/다른 시청자 기록을 제공하지 않습니다. HTTP Range 요청과 `private, no-store` 캐시 정책을 지원합니다.

다른 더미 스팀 서버가 재생 요청을 대신 보내면 소켓 IP는 그 프록시 서버의 IP가 됩니다. 실제 시청자 IP가 필요하면 그 배포 서버의 접속점에서 기록하고, 인증된 신뢰 프록시 연계를 별도로 구현해야 합니다. 임의 HTTP 헤더를 그대로 신뢰하면 안 됩니다.

## 코드와 실행 환경

- Windows C++17 EXE + C++ LibTorch DLL + HTML/CSS/JavaScript 화면.
- 실행 중 Python 프로세스나 외부 AI API를 사용하지 않습니다. 테스트용 Python은 개발 검증에만 씁니다.
- `config.json`의 기존 LibTorch DLL/FFmpeg/FFprobe 경로를 사용합니다. 다른 PC에 옮길 때 이 경로와 MSVC 런타임을 준비해야 합니다. EXE 한 파일만으로 이동 가능한 배포판은 아닙니다.
- 모델: `models/y_256b_img.jit`. 공식 VideoSeal 1.0 256-bit TorchScript, 약 218 MiB. 해시/출처는 `models/MODEL_INFO.json`.
- `src/server.cpp`: 역할 구분, 시청 요청·장부·HMAC·API·미디어 제공.
- `src/engine.cpp`: VideoSeal 삽입, 4방향 검출, 저장 후 검증.
- `src/alignment.h`: 원본 프레임과의 크기·위치·방향 정렬, 의심 영상만으로 보정.
- `src/bch.h`, `src/watermark_code.h`: BCH와 형식별 인증. 발급 장부나 예상 시청자 ID 없이 복원.
- `src/common.h`: BCrypt, UTF-8, 파일 저장, FFmpeg 자식 프로세스.
- `web/index.html`, `app.js`: 제작자 화면. `web/watch.html`, `watch.js`: 시청자 화면.
- `data/`: 원본·사본·검사 파일·장부·DPAPI 키·관리 접근 링크. 제작자 PC 내부 자료입니다.
- `build.cmd`: Visual Studio 2022 + LibTorch로 EXE/DLL 빌드. `FORENSIC_TORCH`로 LibTorch 위치 지정 가능.
- `build_server.cmd`: 서버만 빌드. 해당 EXE가 실행 중이면 먼저 종료합니다.
- `Forensic_G.exe --self-test`: 페이로드 인증/오류 보정 검사, 실제 장부를 읽거나 수정하지 않음.
- v3 코드 검사: `tests/codec_native.cpp` (297개 오류 정정·위조 거절 검사). 실제 영상: `tests/robust_v3.py`.
- 시청 요청 분리 테스트: `tests/viewer_and_flip.py`. 이전 `integration.py`, `robustness.py`, `http_media.py`는 v1 수동 발급 구조의 역사적 테스트입니다.

AI 학습 차단, 복제 방지, 새로 생성한 게임/영상 추적, 물리적 기기 신원 확인 기능은 없습니다.
